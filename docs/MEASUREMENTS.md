# Local ingredient conversion

Original ingredient names, quantity strings, unit strings, and notes remain authoritative. All conversions are computed from those originals; toggling never writes rounded amounts. This also holds through edits, revision restore, database upgrades, and single-file Markdown backups.

## Modules and provenance

`src/lib/conversion/units.ts` defines dimensioned units and source conventions; `quantity.ts` handles cautious parsing; `catalog.ts` contains versioned, sourced ingredient profiles; `identity.ts` resolves names and checks preparation; `format.ts` formats amounts; `suggestions.ts` validates correlated AI suggestions; `migrate.ts` upgrades old records. `measurements.ts` orchestrates display conversion. These modules perform no network requests. The versioned measurement display preference remains in localStorage (`recipe-measurements-v1`).

Each profile has a stable ID, catalog version, actual reference mass and volume, preparation assumptions, aliases, and source URL. Weights are kitchen approximations. Most reference measures come from [King Arthur's ingredient weight chart](https://www.kingarthurbaking.com/learn/ingredient-weight-chart), checked 2026-10-15. Coconut flour and all-purpose flour have separate profiles. Olive oil has its own reference; generic milk, generic oil, canola, and sunflower oil are deliberately not assigned a surrogate density. Whole milk uses an approximate reference within the [FAO milk density range](https://www.fao.org/4/y3548e/y3548e06.htm). Water uses a near-room-temperature kitchen approximation; see [NIST culinary guidance](https://www.nist.gov/pml/owm/metric-si/metric-kitchen/metric-kitchen-culinary-measurement-tips). Brand, temperature, filling technique, and packing can change measured weight; use a scale when precision matters.

Saved identity decisions record `local`, `ai`, `user`, or `legacy` origin, exact identifying context, catalog version, and optional explicit user confirmation of reference assumptions. Legacy ingredientType strings are retained for historical fidelity but never trusted over ingredient text. Local aliases resolve first, except that an explicit user profile takes precedence while its context and preparation remain compatible. Stale or unknown identities cannot authorize a density conversion. Catalog upgrades require inferred identities to be revalidated and manual choices to be confirmed again.

## Source units versus display preference

Mass-to-mass and volume-to-volume use deterministic unit factors; unknown ingredients are never assumed to have water's density. Mass-to-volume or volume-to-mass requires a verified, preparation-compatible profile. Metric normally displays dry ingredients by mass and liquids by volume. Cups / Spoons displays **US customary** volumes.

The independent source convention is stored per ingredient: US customary, 250 ml cup / 15 ml tablespoon / 5 ml teaspoon, 240 ml cup / 15 ml tablespoon / 5 ml teaspoon, Australian 250 ml cup / 20 ml tablespoon / 5 ml teaspoon, or unknown. Existing recipes retain the US convention, explicitly labelled assumed. A US cup is 236.5882365 ml, with 16 tablespoons or 48 teaspoons; see [NIST conversion factors](https://nvlpubs.nist.gov/nistpubs/Legacy/LC/nbslettercircular1098.pdf). Explicit `US cup`/spoon text overrides the default source convention. Unknown conventions retain source cup/spoon amounts. Changing the display preference never changes the source convention. Generic cups/spoons in screenshots remain assumptions unless explicit unit text establishes otherwise.

## Conservative resolution and formatting

Local matching normalizes case, accents, Greek final sigma, and whitespace. Safe English/Greek aliases and a small set of harmless trailing qualifiers such as `divided` are supported. It retains meaningful forms and qualifiers. `brown sugar` needs `packed` in its name or notes (or explicit user confirmation); `coconut flour` never inherits a saved `flour` classification. Sifted/heaped, loosely packed, melted/whipped, chopped/ground/cooked, and other unsupported forms remain original when reference preparation is uncertain. These checks apply across both display modes and also to ml-to-grams. Direct mass conversions remain available regardless of preparation. Spaced Greek abbreviations such as `κ. σ.` are recognized.

Unicode and ASCII fractions, mixed fractions, leading decimals, and decimal commas are supported. Auto parsing rejects `1,000` / `1.000`, which may mean one or one thousand. The user can explicitly choose English or Greek number formatting; no source locale is inferred solely from the ingredient language. Ranges, vague amounts, unsupported units, and conflicting preparation remain original with an explanation.

Familiar fractions are used only within 1% relative error. Decimal display uses four significant digits with the same relative-error bound, avoiding the previous fixed-two-decimal error for tiny amounts. Amounts below 1/64 US teaspoon stay original as impractical spoon measures. No underlying numeric precision or saved string is rounded.

## AI integration and review

Screenshot extraction includes optional constrained `profileId` suggestions alongside original ingredient text in its existing request. Local matching is preferred. Re-estimation sends current title/ingredients/instructions and fresh category/tag vocabulary, plus only unresolved or stale eligible identity targets. Valid local/accepted decisions, explicit user choices, and Keep original choices are reused without identification work. There is no additional identification request. Both flows keep the existing maximum two format attempts under one 80-second deadline.

The provider receives catalog IDs, aliases, and preparation descriptions, never authority to create density factors. Unknown stays null. AI suggestions must pass catalog, preparation, and local lexical-evidence checks. Beyond exact local aliases, the current conservative AI validation permits recognized alias words in a different order; unknown brands/modifiers and unsupported forms require explicit manual selection. A model's confidence is not evidence. This intentionally sacrifices some automatic matches rather than making unsafe conversions.

Re-estimation returns metadata and ingredient suggestions separately. Each target has a request-local UUID, ingredient index within the submitted snapshot, and fingerprint of identifying context. Response/request IDs, unique references, catalog version, and fingerprints are checked. The UI maps references to stable editor row IDs, compares exact context and the prior decision again on acceptance, and rejects removed or stale rows. Reordering is safe; concurrent quantity edits are retained. Accepting a metadata field cannot accept a profile. Every profile has separate Accept/Reject controls. No request IDs are persisted.

The editor provides manual profile selection, preparation confirmation, independent source number/convention settings, and **Keep original measurement**. Selection cannot override explicitly incompatible preparation. Changing identifying text keeps the saved decision for review but disables stale use until revalidated/confirmed. Original amounts, direct conversion versus ingredient approximation, assumed source conventions, and unsupported explanations are visible in details. All accepted decisions and overrides remain local and work offline. Rendering, toggling, opening, reloading, and quantity edits make zero AI calls.
