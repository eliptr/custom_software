# Architecture

## Components and data flow

`src/app/page.tsx` renders the client `RecipeApp`. Its collection, detail, and editor views all use the same `/` application shell, avoiding uncached detail URLs. Radix Dialog provides modal focus trapping, keyboard escape, and accessible titles. Owned button/modal primitives follow the shadcn approach. CSS uses warm monochrome tokens, serif headings, touch targets, safe areas, and system/light/dark themes.

`ThemeChrome` synchronizes the single `theme-color` meta tag with the resolved CSS background after hydration, manual theme changes, or system appearance changes. An early head script restores the saved theme without mutating React-owned metadata before hydration. Both HTML and body paint the app background. Installed iOS uses `black-translucent` status-bar metadata plus a fixed dark safe-area backdrop, with added header height to keep controls below the status icons. The backdrop preserves contrast in light mode; native iOS rendering remains a physical-device check.

`src/lib/recipe.ts` defines one strict Zod content model and the persistence extension (UUID + timestamps). Optional semantic fields are always present and nullable; tags are always an array. Quantity is a string or null, preserving fractions, Greek text, and units rather than forcing a numeric representation. Drafts may have an empty title; saved recipes must have a nonblank title. Unicode is retained exactly; search separately removes accents and normalizes Greek final sigma. No HTML from recipe strings is rendered.

`src/lib/db.ts` owns Dexie database version 4. Transactional upgrades from versions 1, 2 and 3 use deterministic `conversion/migrate.ts` normalization, including historical snapshots. Original names, quantities, units, notes, dates, IDs, and history are preserved; old classifications become unverified legacy hints and unspecified cup conventions become labelled US assumptions. Recipes retain the same UUID key/indexes and `useLiveQuery` updates. Writes and merge/replace validate atomically. Incoming recipe content is authoritative for matching UUIDs; merge unions notes and immutable revisions by stable IDs, rejecting conflicting revision contents. Replace restores exactly the reviewed file. Different UUIDs remain separate recipes.

## Screenshot extraction

1. The browser accepts 1–6 JPEG/PNG/WebP files, at most 20 MB each. It decodes locally, rejects extreme dimensions, scales the longest side to at most 1800 pixels, and converts to JPEG. Combined decoded bytes must be at most 2.8 MB, each at most 1.5 MB.
2. The user enters a separate private app code (memory only). A same-origin POST sends images and the current collection vocabulary to `/api/extract`. Category/tag IDs derive from exact existing labels (`category:<name>`, `tag:<name>`), stable across requests and backups without a cloud taxonomy. No `NEXT_PUBLIC_` key is used. Original files and prepared images never enter IndexedDB, localStorage, or a file server.
3. The Node route checks the token using fixed-length SHA-256 digests and timing-safe comparison, enforces origin and JSON type, streams the body with a 4,000,000-byte cap, validates base64/MIME signatures, deduplicates identical image data, and consumes a rate-limit slot.
4. `RecipeExtractor` is the provider boundary. `DeepSeekExtractor` sends every screenshot in one Chat Completions vision message. `deepseek-flash` image support and JSON output were checked against official documentation on 2026-10-14: [vision](https://api-docs.deepseek.com/guides/vision/), [JSON mode](https://api-docs.deepseek.com/guides/json_mode/). The prompt treats screenshots as untrusted content, preserves language, forbids inventing ingredients/amounts/instructions, and permits reasonable metadata estimates with explicit provenance. Only supplied existing category/tag IDs may be selected; unknown IDs are removed server-side. The local collection is authoritative because recipes have no cloud database. Adding another provider requires implementing this interface; the UI/schema need not change.
5. The provider uses JSON mode, a JSON Schema generated from the shared Zod extraction schema in its prompt, and 6,000 output tokens. An empty, malformed, or schema-invalid model output triggers at most one automatic regeneration from the same screenshots with stricter format guidance. Both attempts share one 80-second deadline and the caller's cancellation signal. HTTP/quota errors, invalid service envelopes, and truncated output are not automatically retried. A second invalid output reports a format error instead of blaming screenshot clarity. No raw model response is logged or fed back into the retry. Normalization supplies null only for omitted optional fields, converts explicit numeric quantities to strings, removes exact duplicates, and flags missing quantities and conflicting ingredient entries. Ingredients-only screenshots produce a valid draft with empty instructions and a review warning; the user can save it and add steps later. A total duration is not presented as explicitly extracted cooking time; any justified prep/cook split is marked estimated. Temperatures include Celsius, cooking method, and per-value provenance. AI output cannot claim user provenance. Model accuracy still requires user review.
6. The editor displays warnings and the draft. Only Save assigns UUID/timestamps and writes IndexedDB. Cancel removes the temporary inputs. Nothing is saved automatically by extraction.

DeepSeek receives the screenshots to process them; its data handling policy applies. The app does not retain screenshots or log request bodies. Failed requests may still consume the quota and provider credits. One authorized upload consumes one firewall slot and can make up to two billable provider calls if format recovery is needed. HEIC is deliberately rejected with conversion guidance.

## API access and quotas

All paid requests require an exact match to the nonempty private `APP_ACCESS_TOKEN`; there is no minimum code length. Blank configuration and the explicit `REPLACE_ME` placeholder disable extraction. Invited users share that code and your AI quota; recipes remain separate on each device. Rotating the code revokes it for everyone. Vercel Deployment Protection is a separate access gate for protected previews.

Production calls `@vercel/firewall`'s `checkRateLimit` for rule ID `recipe-extraction`, with a SHA-256 hash of the validated app code and deployment environment as the bucket key. Caller IP cannot split the shared quota. Only the destination host and IP forwarding headers are supplied to the SDK; the app code, unrelated cookies, and uploaded images are not forwarded. The SDK adds Vercel's system-managed automation bypass secret to its internal request when configured. A three-second timeout bounds the check. Missing-rule and blocked results, network errors, and timeouts return 503 before DeepSeek is called; exhausted quota returns 429 with a conservative ten-minute Retry-After.

The published dashboard rule defines the production window and limit; the recommended fixed window is 10 requests / 10 minutes, compatible with Hobby's maximum window. Vercel's counters are regional, so traffic served in different regions can consume separate buckets. They survive function cold starts without a recipe database or Redis service. Local development/tests use process memory with the same recommended window; production outside Vercel fails closed rather than relying on process-local counters. See [Vercel setup](DEPLOYMENT.md) for the required dashboard configuration and optional edge protection against unauthorized traffic.

Request-size limits also enforce bodies without Content-Length. All API responses are no-store; service workers exclude `/api/` and all POST requests. API secrets are never returned to the browser. HTTPS is required for deployed use.

## Markdown and offline caching

`src/lib/markdown.ts` serializes every supported field into one canonical, versioned Markdown file. Recipes sort by UUID for deterministic output. A bounded parser validates structure, field order, consecutive steps, IDs, and Zod semantics. Blank separator lines, UTF-8 BOM, and CRLF are accepted. Duplicate IDs within a file are rejected. See the complete format specification.

The supported collection capacity is 2,000 recipes and 5 MiB of canonical Markdown. CRUD and merge validate this capacity inside the write transaction, guaranteeing that accepted saved collections can be restored from their export. Capacity errors do not modify existing data.

At build time the worker cache name gets a hash of source, public assets, build configuration, and lockfile. Installation fetches the root HTML, discovers its hashed JS/CSS assets, and caches those plus manifest/icons before completing. Navigation uses the network first and falls back to that installed shell offline. Immutable static assets use cache-first. A new worker waits; the app offers Update only on the idle collection screen, protecting editor drafts, cooking checklists, notes, and restore confirmations. Activation removes older Recipe Tracker caches and claims clients; an approved controller change reloads. IndexedDB is independent of the cache and is never cleared by updates. A failed worker installation keeps the previous worker active. Unsupported storage or operation failures have user-visible feedback.

Themes and the versioned measurement-system preference are stored in localStorage. Ingredient display reads a saved metric/US pair, or performs exact same-dimension math before falling back to the original. Rendering, opening, reloading, quantity rescaling, and toggling make no AI calls. See MEASUREMENTS.md. Cooking checkboxes are temporary view state. There is no cross-device sync; Markdown is the portable backup.

## Metadata suggestions, notes, and revisions

`RecipeExtractor.estimate` reuses the same DeepSeek request/timeout/format-retry transport. `/api/estimate` authenticates, bounds and validates the current recipe/vocabulary, and consumes the same `recipe-extraction` bucket before contacting the provider. It transmits current title, ingredients, and instructions; cooking notes and revision history are never sent. There are no new environment variables or dependencies.

`MetadataSuggestions` fetches fresh vocabulary and builds conversion targets for EVERY ingredient, including existing pairs and noncatalog ingredients. Updated requests add `conversionVersion: 1` and a `conversions` object with request UUID, unique row references, snapshot indices, and fingerprints including quantity/name/unit/notes/full measurement context. The provider returns `{metadata, requestId, conversionSuggestions}`. Each proposal carries a validated pair, input snapshot, model/prompt version, date, and assumptions. Server/client normalization enforces numeric/unit bounds and exact unit relationships; malformed individual rows are discarded without losing valid metadata or other rows. Model format failures retain the shared maximum two attempts under one 80-second deadline. There is no additional identification/conversion request.

The UI maps request references to stable editor row IDs and compares full exact input plus prior saved decision before applying. Changed quantities, other context, removed/re-added rows, reordering, and concurrent accepted decisions cannot target the wrong row. Each metadata field and measurement pair has independent approval; Save persists accepted pairs. Failed/invalid/unavailable proposals do not erase existing values. Source convention and Keep original remain explicit local controls. Quantity-only edits rescale from the immutable accepted basis; other identifying edits disable its use until refreshed. Screenshot equivalents populate a reviewable unsaved draft.

Both endpoints retain older installed-client shapes: no extraction flag returns the original five ingredient fields; extraction flag 3 retains identity/context fields without saved equivalents. Unflagged estimate requests still return flat metadata, or the legacy profile envelope when an identification payload is supplied. New flag 1 negotiates equivalents, independent of database/Markdown version 4. Legacy catalog/profile modules remain for this compatibility path and historical fidelity, not as a requirement for current AI estimates. Notes/history and existing saved pairs are not sent to the model as estimation evidence; it receives current originals and steps.

`RecipeMetadata` is shared by cards, details, and revision previews. It uses cookTime alone, never prepTime + cookTime. Each temperature retains its method. Saved-equivalent schema, normalization, correlation, exact units and bounded display formatting are separate modules. Details show the selected amount, `≈` for AI estimates, and the original; detailed provenance/assumptions stay in editor controls. No shared density library is required.

`RecipeJournal` writes dated/rated notes through atomic CRUD helpers. Ordinary recipe saves do not append revisions. An explicit revision save deep-clones complete recipe content with a UUID, date, and optional description; snapshots exclude nested notes/history. Confirmed restore appends a safety snapshot of current content and restores the chosen content while retaining all notes and earlier revisions. Validation and the 5 MiB backup check happen within the same IndexedDB transaction; failures never prune history or partially write. Closed revisions defer rendering their full content until opened.

IndexedDB version 4 and Markdown format 4 add nullable saved equivalents to ingredients and revision snapshots. Versions 1–3 migrate/import deterministically without altering original values, dates, journals or historical decisions. Notes, history, temperatures and provenance remain in the same single file. See RECIPE_FORMAT.md for the grammar and merge/capacity rules. Display preferences remain device settings outside backups.
